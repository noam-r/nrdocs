# nrdocs 2.0 Security and Resource-Limit Contract

## Status

Normative and locked for nrdocs 2.0.

This document defines the security behavior and bounded-resource rules used by
the CLI, Worker, D1 schema, publication protocol, and reader. Implementations
must not substitute different algorithms, lifetimes, or limits without changing
the specification version.

## Security Boundary

nrdocs accepts untrusted publisher credentials, archives, Markdown-derived
documents, reader passwords, URLs, and request metadata. It serves only
CLI-produced, independently validated artifacts. It does not execute publisher
HTML, JavaScript, CSS, SVG, templates, plugins, or server-side source builds.

Cloudflare administrator authority is used only by the local CLI. There is no
administrator HTTP API in the Worker.

## Publishing Tokens

### Token format

A publishing token is exactly:

```text
nrd_pub_<43 base64url characters>
```

The suffix encodes 32 cryptographically random bytes using unpadded base64url.
The complete token must match:

```regex
^nrd_pub_[A-Za-z0-9_-]{43}$
```

The CLI generates tokens with the operating system cryptographic random-number
generator. A malformed token is rejected before any database lookup.

### Stored verifier

D1 stores only `sha256:<64 lowercase hexadecimal characters>`, where the digest
is SHA-256 over the exact ASCII token. Plain SHA-256 is intentional here because
the token contains 256 bits of random entropy and must be generated by the CLI
without a Worker-only secret. The plaintext token is shown once and is never
logged or recoverable.

Digest comparison is constant-time. Unknown, malformed, expired, revoked, and
wrong-site credentials all produce the same public `invalid_token` response.

### Lifetime

`nrdocs token issue --ttl <duration>` uses the grammar defined in
`02-cli-configuration-and-credentials.md`. The maximum accepted TTL is 365 days
or 31,536,000 seconds. Omitting `--ttl` creates a token with no expiry.

The server uses its own time. A token is expired when `now >= expires_at`; no
clock-skew allowance applies to a client-supplied time.

### Last-used metadata

Only successful authentication may update `last_used_at`. The Worker attempts a
conditional update no more than once per token per 15 minutes. This update is
best-effort and never changes the authentication result.

## Reader Passwords

### Input rules

A reader password contains 1 through 256 Unicode scalar values. It is used
exactly as entered: no trimming, case conversion, or Unicode normalization
occurs. No composition rules are imposed.

The CLI reads passwords from a hidden interactive prompt, confirms new
passwords, and never accepts them as command-line arguments or prints them.

### Verifier format

The CLI derives the verifier with PBKDF2-HMAC-SHA-256 using:

- 100,000 iterations (Cloudflare Workers reject PBKDF2 counts above 100,000);
- a fresh 16-byte cryptographically random salt; and
- a 32-byte derived key.

The stored form is:

```text
pbkdf2-sha256$100000$<unpadded-base64url-salt>$<unpadded-base64url-key>
```

The Worker verifies using the iteration count written in the string. It accepts
only `100000` and the legacy label `600000`. A `600000` label is tried at
600,000 iterations when the runtime allows it, and at 100,000 otherwise, so
verifiers minted while the CLI hashed at 100,000 but labeled 600,000 still
match. The Worker rejects every other algorithm, parameter count, encoding,
salt length, or key length. It compares derived keys in constant time. There is
no pepper: password verification occurs in the Worker while password setup
occurs in the administrator CLI, and sharing a pepper would enlarge the secret
boundary.

## Reader Sessions

### Signing key

The Worker secret `NRDOCS_SESSION_KEY` is 32 cryptographically random bytes. The
first deployment creates it; upgrades preserve it through explicit binding
inheritance. The CLI never reads or persists it. An explicit operator rotation
invalidates every reader session and is not part of ordinary deployment.

### Cookie and token

The cookie name is `__Host-nrdocs-s-<site-id>`. Site IDs use the safe identifier
alphabet defined in the data-model specification.

The value is:

```text
v1.<base64url(canonical-json)>.<base64url(HMAC-SHA-256)>
```

Canonical JSON contains only `v`, `site_id`, `generation`, `iat`, and `exp`.
Times are integer Unix seconds. The signature covers the literal `v1.` prefix
and encoded payload.

Sessions have a 12-hour absolute lifetime and are not refreshed. The cookie has
`Max-Age=43200`, `Path=/`, `Secure`, `HttpOnly`, and `SameSite=Lax`, with no
`Domain`. Validation requires a valid signature, the requested site ID, the
current access generation, `now < exp`, and `iat <= now + 60 seconds`.

Logout clears the exact cookie using `Max-Age=0` and otherwise identical cookie
scope. Session values are never placed in URLs, HTML, JavaScript-visible
storage, or local storage.

## Form and CSRF Protection

Password-access and logout POSTs require all of the following:

- an exact `Origin` match to the current canonical origin;
- `application/x-www-form-urlencoded` content;
- a body no larger than 4 KiB;
- exactly the documented form fields; and
- a valid signed CSRF value.

Missing or mismatched `Origin` is rejected with 403. The CSRF value binds the
action, site ID, safe return path, issue time, and a random 128-bit nonce. It is
HMAC-SHA-256 signed with `NRDOCS_SESSION_KEY`, expires after 10 minutes, and is
never accepted for another action or site. Return-path validation is defined in
`09-fixed-reader-and-serving.md`.

Its exact representation is
`v1.<base64url(canonical-json)>.<base64url(HMAC-SHA-256)>`. The canonical JSON
contains only `v`, `action`, `site_id`, `return_path`, `iat`, and `nonce`; the
signature covers the literal `v1.` prefix and encoded payload. `action` is
exactly `access` or `logout`, `iat` is an integer Unix second, and `nonce` is
unpadded base64url for exactly 16 random bytes. Duplicate, missing, unknown, or
wrongly typed fields are rejected.

## Rate Limiting

Worker Rate Limiting bindings are an abuse-control layer, not an accounting or
authorization mechanism. Keys use a one-way digest of the relevant source
value; plaintext IP addresses and tokens are not stored in keys or logs.

| Operation                                                  |              Limit |
| ---------------------------------------------------------- | -----------------: |
| Password attempts per site and source IP                   |  10 per 60 seconds |
| Password attempts per site, all sources                    | 100 per 60 seconds |
| Requests with invalid publishing credentials per source IP |  30 per 60 seconds |
| Resolve-target requests per valid token                    | 120 per 60 seconds |
| Publish requests per site and valid token                  |  10 per 60 seconds |
| Publication API requests per instance                      | 300 per 60 seconds |

Exceeding any applicable limit returns HTTP 429, code `rate_limited`, and
`Retry-After: 60`. Cloudflare's rate-limiting counters may be locally scoped and
eventually consistent; correctness must not depend on exact global counting.
Every password submission, successful or not, consumes both applicable
password counters before password derivation. There is no durable account or
site lockout state.

## Publication Lock

A site has at most one publication lock. Acquisition sets a random lock ID,
`publish_lock_acquired_at`, and `publish_lock_expires_at` atomically.

- Lease duration: 120 seconds.
- Renewal threshold: when 60 seconds or less remain.
- Renewal result: `expires_at = server_now + 120 seconds`.
- Hard lifetime: 10 minutes from `publish_lock_acquired_at`.
- Renewal requires the same lock ID, an existing site, and the same
  still-usable publishing token.

An expired lock may be atomically reclaimed. A competing request receives 409
`publish_in_progress` and `Retry-After` equal to the remaining whole seconds,
rounded up and clamped to 1 through 120. Promotion and release recheck lock
ownership. A request can never renew or release another request's lock.

## Resource Limits

The CLI prechecks these values; the Worker independently enforces them. Crossing
any limit fails the publication before promotion.

| Resource                          |                               Maximum |
| --------------------------------- | ------------------------------------: |
| Compressed publication request    |                                25 MiB |
| Total uncompressed artifact bytes |                               100 MiB |
| Uncompressed-to-compressed ratio  |                                  20:1 |
| Manifest document                 |                                 1 MiB |
| Files declared by the manifest    |                                 1,000 |
| Published pages                   |                                   500 |
| Published assets                  |                                   500 |
| Published attachments             |                                   200 |
| One source Markdown file          |                                 1 MiB |
| One complete page HTML document   |                                 2 MiB |
| One raster image                  |                                10 MiB |
| One attachment                    |                                25 MiB |
| Mermaid blocks per page           |                                    50 |
| Mermaid source per block          |                                64 KiB |
| Archive path in UTF-8             |                             512 bytes |
| One archive path segment in UTF-8 |                             128 bytes |
| Attachment display filename       | 160 scalar values and 255 UTF-8 bytes |

The archive contains only regular files. Directories are implicit. Symlinks,
hard links, devices, FIFOs, sparse entries, absolute paths, backslashes, empty
segments, `.` segments, `..` segments, NUL, and portable-key collisions are
rejected as defined by the filesystem and artifact specifications.

One site may have exactly one in-progress publication. Publication request
processing has a five-minute request deadline and a ten-minute hard lock
lifetime. There is no application-defined global concurrency queue; instance
rate limits and Cloudflare platform limits bound aggregate work.

## Content and Browser Boundary

The renderer escapes all Markdown-originated text. Publisher-controlled raw
HTML is rejected, as are SVG and all publisher-controlled behavior-bearing web
assets. The Worker validates complete stored page documents against the exact
allowlist in `09-fixed-reader-and-serving.md` and stores accepted bytes
unchanged.

Reader, form, API, error, and attachment responses use the security headers and
cache rules in the fixed-serving specification. Site content is never served
from a public R2 endpoint.

## Logging and Error Redaction

Logs must redact or omit:

- `Authorization`, `Cookie`, and `Set-Cookie` values;
- publishing tokens and stored verifiers;
- reader passwords and password verifiers;
- Cloudflare credentials and the session signing key;
- request and response bodies; and
- URL query strings.

Before emitting any free text, the logger replaces strings matching the
publishing-token pattern with `[REDACTED_TOKEN]`. Safe request IDs, opaque site
and artifact IDs, status codes, durations, byte counts, and validation codes may
be logged. Public errors never contain stack traces, SQL, object keys, verifier
material, parser internals, or platform credentials.

## Security Acceptance Criteria

1. Token format, hashing, expiry, revocation, and indistinguishable failure
   behavior have contract tests.
2. Password verifier fixtures cover Unicode, exact-byte behavior, bounds,
   malformed encodings, and constant-time comparison paths.
3. Session tests cover signature, site binding, generation invalidation,
   lifetime, cookie attributes, logout, and key rotation.
4. CSRF tests cover missing and foreign origins, action/site substitution,
   expiry, and unsafe return paths.
5. Rate-limit tests assert stable 429 responses without treating counters as
   authorization state.
6. Archive and HTML validators have adversarial fixtures at every numeric and
   structural boundary.
7. Secret-pattern tests verify that CLI output, Worker errors, and structured
   logs do not expose protected values.
8. A failed validation or exhausted lock can never change the current artifact.
